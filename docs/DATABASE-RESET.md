# Очистка тестовых данных перед запуском

Операторская команда `php bin/console reset-data` проверяет схему, целостность и внешние ключи SQLite и показывает только количество строк в бизнес-таблицах. Без `--confirm` данные не меняются. Команда требует остановленных `poll` и `worker`; блокировки обоих процессов и резервного копирования удерживаются до завершения. Достаточно `DATABASE_PATH`, секреты и внешние API не используются.

`reset-data --confirm` сначала создаёт согласованную копию SQLite, проверяет очистку отдельной копии этой базы и только после успешной репетиции очищает рабочую базу одной транзакцией. Удаляются `jobs`, `translations`, `drafts`, `broadcasts`, `contacts`, `staff_sessions`, `users`; почтовый таймер сбрасывается. Неизвестная схема, неудачная копия или репетиция останавливают операцию до удаления рабочих данных. Ошибка транзакции отменяет все её изменения.

Сохраняются применённые миграции, `processed_updates`, `sqlite_sequence` и служебные отметки защиты. Новые номера черновиков, рассылок и заданий продолжают прежнюю последовательность. Начальная ревизия новой анкеты выше любой ревизии, существовавшей перед очисткой, и повышается при повторной очистке. Конфигурация, роли из окружения и Gmail OAuth расположены вне базы и этой командой не изменяются.

После очистки `Kernel` записывает, но не выполняет updates, у которых `message.date` не больше секунды очистки. Для callback проверяется дата исходного сообщения с кнопкой: старые кнопки регистрации и сотрудников остаются безопасными даже при новом нажатии. Отсутствующая или недоступная дата также запрещает действие после очистки. Новое сообщение в ту же секунду будет отброшено; начинайте проверку `/start` со следующей секунды. Для этой защиты необходим новый код `Kernel` и `SqliteStore` в работающем `poll`: старый образ после очистки запускать нельзя.

Копия хранится в `/data/backups/before-reset/reset-<случайный ID>/broadcast-<время>.sqlite`; каталог имеет режим 0700, файл 0600 на Linux. Каждая очистка использует отдельный каталог, поэтому обычная семидневная ротация не удаляет копию для отката. Файл содержит персональные данные и секреты очереди: не выводите содержимое и не включайте его в релиз. Копия в том же томе не защищает от потери диска; перед запуском вынесите её на отдельный защищённый носитель или в `/root/bot-backups` как минимум вне Docker-тома. Удаление строк не является гарантированным стиранием свободных страниц или исторических копий SQLite. Уже отправленные Telegram-сообщения и письма сохраняются у получателей.

## Точная процедура на сервере

Сервер: `/opt/telegram-broadcast`, архивный релиз без Git checkout. Подготовьте и проверьте код обеих веток локально, передайте только исходники архивом с проверкой SHA-256. `.env`, `secrets`, SQLite и локальные зависимости в архив не включать. Сохраните прежний образ и архив исходников для отката. Сборки выполняются до остановки бота; основной Compose и Gmail используются вместе.

```bash
cd /opt/telegram-broadcast
df -h /
docker compose -f compose.yaml -f compose.gmail.yaml config --quiet
docker compose -f compose.yaml -f compose.gmail.yaml ps
docker compose -f compose.yaml -f compose.gmail.yaml run --rm worker backup
docker build --target test -t telegram-broadcast:test .
docker build --target production -t telegram-broadcast:local .
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll check
docker compose -f compose.yaml -f compose.gmail.yaml stop poll worker
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll reset-data
```

Зафиксируйте количества и подтвердите, что база содержит только предназначенные для удаления тестовые данные. Затем:

```bash
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll reset-data --confirm
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll reset-data
```

В событии `reset_complete` обязательны `rehearsal_verified=true`, нули во всех `after`, путь `backup`, `cutoff`, `revision_floor`, `next_update`. Повторная проверка без `--confirm` должна показать нули. При сбое оставьте процессы остановленными, проверьте состояние без новой очистки и выберите восстановление по зафиксированной копии.

Скопируйте указанную согласованную копию из тома в `/root/bot-backups` через одноразовый контейнер или `docker cp`, проверьте SHA-256 обоих файлов и установите 0600. Не копируйте активные SQLite/WAL-файлы. Проверьте только наличие и неизменность настроек и OAuth, не печатая их содержимого. После этого:

```bash
docker compose -f compose.yaml -f compose.gmail.yaml up -d --no-build poll worker
docker compose -f compose.yaml -f compose.gmail.yaml ps
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll check
docker compose -f compose.yaml -f compose.gmail.yaml logs --since=5m --tail=100 --no-color
```

Автоматические тесты проверяют регистрацию с нуля через Kernel/Worker и новое обязательное одобрение, освобождение контактов, отсутствие догоняющей тестовой рассылки, старые кнопки, накопленные updates, повторы очистки, блокировки, резервную копию, восстановление и откат при ошибке. Ручная проверка `/start` и регистрации на сервере выполняется оператором. После ручной проверки тестовая анкета не должна остаться перед приёмом клиентов: запланируйте повторную очистку или финальную процедуру задачи 11.

## Откат

Остановите оба процесса. Сохраните текущее состояние через `backup` и восстановите именно зафиксированную копию:

```bash
docker compose -f compose.yaml -f compose.gmail.yaml stop poll worker
docker compose -f compose.yaml -f compose.gmail.yaml run --rm worker restore /data/backups/before-reset/reset-ID/broadcast-TIMESTAMP.sqlite --confirm
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll migrate
```

Восстановление возвращает тестовую аудиторию и очередь, поэтому не запускайте процессы автоматически после отката. Сначала решите, какие старые задания допустимо выполнять. Возвращать прежний образ можно только вместе с согласованным прежним состоянием БД; для очищенной базы требуется код защиты от старых действий. Не используйте `down -v`, удаление файла БД или обнуление `sqlite_sequence`.
