# Отправка отдельных писем через Gmail OAuth

Бот поддерживает два транспорта: `MAIL_TRANSPORT=smtp` (прежний SMTP) и `MAIL_TRANSPORT=gmail` (Gmail API). Каждому одобренному пользователю отправляется отдельное обычное текстовое письмо с одним адресом в `To`, без общих списков, CC и BCC. Переводы, очередь, пауза между письмами, повторы и отдельная доставка в Telegram сохраняются. API не гарантирует попадание во входящие: отчёт означает принятие письма почтовым сервисом, а не доставку или прочтение.

Нужен аккаунт отправителя Gmail, OAuth Client ID типа **Desktop app**, JSON этого клиента и refresh token. Service account JSON для обычного Gmail не подходит. Веб-клиент можно использовать с уже полученным токеном, но локальная команда ниже рассчитана на Desktop app.

## 1. Подготовить проект Google Cloud

1. Откройте проект, в котором создан ваш OAuth-клиент.
2. В **APIs & Services → Library** включите **Gmail API**.
3. В **Google Auth Platform → Branding / Audience / Data Access** настройте название приложения и почту разработчика. Для обычного Gmail используется External audience.
4. Добавьте разрешение `https://www.googleapis.com/auth/gmail.send`. Оно позволяет отправлять письма; чтение и удаление почты бот не запрашивает.
5. Пока приложение имеет статус **Testing**, добавьте новую почту отправителя в Test users. Пользователям-получателям не нужно авторизовываться в Google или становиться тестовыми пользователями.
6. В Clients сохраните тип **Desktop app** и скачайте JSON. Для Desktop app не требуется вручную добавлять redirect URI веб-клиента; команда использует временный локальный адрес `http://127.0.0.1:PORT/oauth2callback`.

В статусе External / Testing Google выдаёт refresh token для Gmail со сроком действия **7 дней**. Для постоянной работы переведите проект в **Production**, учитывая требования Google к публикации и верификации для вашего сценария, затем повторите авторизацию. Статус Production не гарантирует бессрочный токен: отзыв доступа, смена пароля и другие условия Google могут потребовать новой авторизации.

## 2. Получить refresh token локально

Запустите авторизацию на своём компьютере с браузером, а не внутри Docker или через SSH на удалённом сервере. PHP должен иметь расширение curl; зависимости проекта должны быть установлены (`composer install`).

В PowerShell из каталога проекта:

```powershell
New-Item -ItemType Directory -Path .\secrets -Force
```

Скопируйте скачанный JSON в `secrets/gmail-client.json`. Не присылайте его содержимое в чат. Каталог secrets исключён из Git и Docker-контекста; файлы нельзя переносить в assets или src.

```powershell
php bin/gmail-authorize .\secrets\gmail-client.json .\secrets\gmail-token.json
```

Команда напечатает ссылку Google. Откройте её **на том же компьютере**, войдите именно в новую почту отправителя и разрешите отправку писем. Локальный обработчик проверяет state и PKCE, затем сохраняет refresh token в `secrets/gmail-token.json`. Токен не выводится в терминал. Письма во время этой процедуры не отправляются; это разовая настройка оператором, вне poll/worker и обработки Telegram updates.

Команда ждёт до 5 минут и отказывается перезаписывать существующий файл токена. При повторной авторизации сначала остановите worker, переименуйте прежний `gmail-token.json` в приватном каталоге, получите новый файл и пересоздайте контейнеры. Сохраняйте старый файл только столько, сколько нужно для восстановления; JSON содержит секрет.

Если операция не завершается: проверьте, что выбран Desktop app, Gmail API включён, нужная почта добавлена в Test users, разрешение gmail.send предоставлено и браузер запущен на том же компьютере. Если Google не выдал refresh token, повторите согласие; при необходимости отзовите прежний доступ приложения в Google-аккаунте и авторизуйте заново.

Страница браузера `Authorization received. Return to the terminal.` означает только получение callback. После неё PHP отдельно обращается к `https://oauth2.googleapis.com/token`; готовность подтверждает сообщение терминала о сохранении refresh token. Команда выводит безопасный этап ошибки: `client` (Desktop JSON), `output` (существующий файл или отсутствующий каталог), `listener` / `callback` (локальный обработчик и согласие), `exchange` (сеть или отказ Google), `save` (запись файла). Ответы Google, коды авторизации и токены не печатаются.

При тайм-ауте/DNS/ошибке соединения на этапе `exchange` проверьте доступ к `oauth2.googleapis.com` из PHP: браузер может использовать другой прокси или маршрут. Попробуйте другую сеть и проверьте правила VPN/межсетевого экрана. При ошибке TLS настройте доверенные CA для PHP (`curl.cainfo`), не отключая проверку сертификатов. При отклонённом или истёкшем коде запустите команду заново и используйте новую ссылку. Повторное открытие старого callback не завершит авторизацию.

## 3. Настроить отправителя

В своём `.env` измените только почтовую конфигурацию:

```dotenv
APP_ENV=production
MAIL_TRANSPORT=gmail
MAIL_FROM_ADDRESS=your-new-account@gmail.com
MAIL_FROM_NAME=Imén Nails
MAIL_REPLY_TO=
MAIL_SEND_INTERVAL_SECONDS=2
GMAIL_OAUTH_CLIENT_FILE=./secrets/gmail-client.json
GMAIL_OAUTH_TOKEN_FILE=./secrets/gmail-token.json
```

Замените адрес на почту, с которой только что вошли в Google. Подмена произвольного отправителя не поддерживается этой инструкцией. SMTP_HOST/PORT/ENCRYPTION/USERNAME/PASSWORD в режиме gmail не используются и могут быть удалены. Параметры Telegram, перевода и SQLite оставьте прежними.

Без Docker пути к JSON читаются из переменных окружения; bin/console сам `.env` не загружает. JSON клиента/токена читаются локально, `check` не обращается к Google и не обновляет токен.

## 4. Запустить с Docker

```powershell
docker compose build
docker compose -f compose.yaml -f compose.gmail.yaml run --rm poll check
docker compose -f compose.yaml -f compose.gmail.yaml up -d
```

`compose.gmail.yaml` монтирует оба файла read-only в `/run/secrets/` и переопределяет пути для poll и worker. Если файл отсутствует, Compose не создаёт вместо него каталог. При следующих командах используйте те же два compose-файла, например:

```powershell
docker compose -f compose.yaml -f compose.gmail.yaml logs --tail=100
```

Не добавляйте compose.test.yaml к этому запуску: он предназначен для Mailpit и принудительно выбирает SMTP. `APP_ENV=test` сам по себе не отключает реальные отправки Gmail.

На сервер передайте два JSON защищённым способом отдельно от исходников, в каталог secrets. Файлы должны читаться пользователем контейнера UID 1000. На Linux установите владельца UID/GID 1000 и права 600, обеспечив доступ к каталогу; на Windows ограничьте ACL нужными пользователями. Не коммитьте файлы, не помещайте их в образ, общие логи или публичную папку сайта.

## 5. Проверить реальную доставку

1. Зарегистрируйте тестового пользователя с почтой, на которой можете проверить входящие, и одобрите его заявку.
2. Подготовьте короткое объявление с темой; одобрите обычного автора либо нажмите «Разослать» для собственного объявления суперадмина.
3. Проверьте отдельно сообщение Telegram и письмо (входящие и спам), а также папку Sent в аккаунте Gmail отправителя.
4. Дождитесь отчёта суперадминистратору. Успех email означает подтверждение API, не попадание во входящие.

При сетевой ошибке, HTTP 429/5xx или временном лимите Gmail очередь делает прежние повторы. При HTTP 401 access token сбрасывается и обновляется на следующей попытке. Ошибки согласия/отозванного refresh token требуют новой авторизации: восстановите доступ, затем используйте `/retry ID`. Уже успешная доставка Telegram и успешные письма не повторяются. Ответы Google и секреты не сохраняются в логах/ошибках jobs.

Сетевой тайм-аут после принятия письма сервером может сделать результат неопределённым; стандартные повторы почтовой доставки не гарантируют отсутствие дубля в таком случае. Малое число получателей не отменяет лимиты Gmail и фильтры спама.

Если письмо попало в спам, это не означает сбой OAuth или отправки: папку выбирает почтовый сервис получателя. Проверьте, что MAIL_FROM_ADDRESS совпадает с авторизованным Gmail-аккаунтом. Для диагностики нужны результаты SPF/DKIM/DMARC и пояснение фильтра из полученного письма, а не полный исходник с адресами. В Gmail доверенное письмо можно отметить «Не спам» и добавить отправителя в контакты; это настройка конкретного получателя, а не гарантия доставки всем пользователям. OAuth-верификация приложения и отдельный адресат в To не гарантируют попадание во входящие. [Справка Gmail](https://support.google.com/mail/answer/1366858?hl=ru).

Официальные источники: [отправка Gmail API](https://developers.google.com/workspace/gmail/api/guides/sending), [разрешения messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send), [OAuth для Desktop](https://developers.google.com/identity/protocols/oauth2/native-app), [сроки refresh token](https://developers.google.com/identity/protocols/oauth2#expiration), [ошибки и лимиты](https://developers.google.com/workspace/gmail/api/guides/handle-errors).
