# Каталог WhatsApp и вложения: локальная проверка и передача разработчику

Текущая задача выполняется локально. Обновление сервера выполняет старший разработчик из проверенного коммита. Доступ root для локальной проверки не нужен. Домен для будущих ссылок: `https://service.imenka.world/download`; наличие DNS-записи не означает готовность обработчика HTTPS.

## Что меняется

При заданных `CONTACTS_MYSQL_DSN`, `CONTACTS_MYSQL_USER`, `CONTACTS_MYSQL_PASSWORD` получатели WhatsApp берутся из MySQL. Анкета WhatsApp отключена, ответы клиентов остаются менеджеру. Telegram сохраняет анкету, одобрение и повторную подачу после `/unsubscribe ID`. Эта команда останавливает все каналы связанного клиента.

Номер связывает каналы. Язык Telegram остаётся из анкеты, WhatsApp — из каталога. Приоритет почты — адрес Telegram; ручной `manual_email` используется при его отсутствии. Для email используется язык Telegram, иначе язык WhatsApp. Каталог читается при подготовке аудитории и перед доставкой; список и языки конкретной рассылки фиксируются снимком. `active=0` останавливает оставшиеся доставки, включая уже подготовленные задания. Временная недоступность MySQL задерживает отправку; не разрешает её по старому списку.

Файлы до 20 000 000 байт, до десяти в объявлении; тема обязательна, текст можно оставить пустым. Переводятся тема и общий текст. Содержимое файлов не переводится. Добавление или удаление файла меняет версию черновика; согласование доступно после скачивания и полного предпросмотра. `/done` завершает комплект. WhatsApp принимает прямой файл до 16 MiB; большие файлы отправляются ссылками. Email отправляется одним письмом; фактический MIME-размер ограничен `MAIL_MAX_MESSAGE_BYTES`, непоместившиеся файлы заменяются ссылками до сетевой отправки.

При потере подтверждения после возможной отправки результат становится `unknown`. Автоматического повтора и замены файла ссылкой в этом случае нет. Сначала нужно проверить приём на стороне получателя; `/retry ID` не повторяет `unknown` и уже принятые части.

## Excel и запрет тестовых отправок клиентам

Предоставленный файл импортируется с `--continuation-row=5 --continuation-row=9`: строки 4–5 и 8–9 — общие контакты. Перед применением выполнить dry-run и сверить SHA-256; затем передать тот же SHA через `--confirm-sha256`. Формат команды описан в [CONTACTS.md](CONTACTS.md). Колонка почты необязательна.

Реальные контакты из Excel хранятся локально в отдельном каталоге `broadcast_contacts_preview`. Он **не подключён к отправляющему worker**. Не использовать его как `CONTACTS_TEST_MYSQL_DSN`: PHPUnit очищает свои тестовые таблицы. Не добавлять реальные номера в тестовый allowlist. Исходный Excel и импортированная БД не включаются в Git.

## Локальные проверки

`compose.contacts-test.yaml` поднимает MySQL на `127.0.0.1:13306`. Учётные данные в этом файле предназначены только для локального тестового контейнера. PHPUnit использует отдельную `broadcast_test` и переменные `CONTACTS_TEST_MYSQL_DSN/USER/PASSWORD`, `CONTACTS_REQUIRE_MYSQL_TESTS=1`. Основной набор тестов обращается к фейковым API и локальным сокетам.

`compose.multichannel-smoke.yaml` вместе с `compose.whatsapp.yaml` добавляет отдельный сервис `smoke`. Он использует собственную SQLite, собственные файлы и MySQL `broadcast_smoke_test`; исходная база тестового бота доступна только для чтения. `inspect` проверяет ранее одобренного получателя из существующего allowlist; `prepare` создаёт один комплект из десяти синтетических файлов без отправки; `run` исполняет только эту очередь; `report` показывает количества и статусы без контактов. Повторный `prepare` в том же томе запрещён. Telegram получает только уже одобренный чат тестового бота, WhatsApp — выбранный ранее разрешённый номер, email — его ранее одобренный адрес. `prepare-files-only` и `prepare-telegram` создают отдельные однократные сценарии, не повторяя старые неопределённые задания. Перевод помечен `LOCAL TEST` и выполняется фейком; рабочий DeepL проверяется отдельными тестами адаптера.

Пример вызова после подготовки изолированной БД и прав тома:

```sh
docker compose -f compose.whatsapp.yaml -f compose.multichannel-smoke.yaml run --rm --no-deps smoke inspect
docker compose -f compose.whatsapp.yaml -f compose.multichannel-smoke.yaml run --rm --no-deps smoke prepare
docker compose -f compose.whatsapp.yaml -f compose.multichannel-smoke.yaml run --rm --no-deps smoke run
docker compose -f compose.whatsapp.yaml -f compose.multichannel-smoke.yaml run --rm --no-deps smoke report
```

Для обычного ручного тестирования тестовый worker должен быть пересобран, а миграции применены под блокировками процессов. `docker compose up -d` само образ не пересобирает. Изолированный `smoke` не запускает poller и не потребляет updates действующего тестового бота.

Ручной локальный стенд запускается с `compose.whatsapp.yaml` и `compose.multichannel-local.yaml`. Каталог `broadcast_live_test` содержит только прежних разрешённых тестовых получателей; первоначальное заполнение — `tools/whatsapp/seed-local-directory.php` (без отправок). Клиентский `broadcast_contacts_preview` не используется. Ссылки в этом ручном стенде пока отключены: до настройки HTTPS можно проверять прямые вложения. На локальном FPM отдельно проверены GET/HEAD, точные байты и 404; внешний HTTPS проверит разработчик при развёртывании.

## Передача старшему разработчику

1. Забрать проверенный коммит, прочитать его `VERIFICATION.md`, собрать `docker build --target test` и production-образ. Новые зависимости PHP: `pdo_mysql`; существующие `intl`, `zip`, `fileinfo` остаются обязательными.
2. До остановки процессов подготовить отдельного пользователя MySQL с доступом только к каталогу. Применить `contacts-migrate`. Импортировать проверенный Excel отдельной командой; импорт не создаёт рассылок. Для рабочих отправок заранее согласовать полный список разрешённых адресатов транспорта: локальный allowlist содержит только тестовые номера. Одного изменения MySQL недостаточно для обхода этого ограничения WppConnect.
3. Остановить `poll`, `worker`, `whatsapp-poll`. Сохранить согласованный комплект: SQLite с WAL через штатный backup, SQL-дамп таблиц `bc_*`, приватное хранилище файлов, отдельный том HMAC-ключа `attachment-keys`, версию образа и исходников. Не публиковать эти материалы в Git.
4. Применить `migrate` к SQLite и повторить `contacts-check`, `check`. Старые миграции не редактируются. При старте worker переносит Telegram-профили через идемпотентный outbox; аудитория не публикуется, пока синхронизация не завершена.
5. Настроить HTTPS `service.imenka.world`. `compose.attachments.yaml` собирает отдельный PHP-FPM `download`, монтирует вложения только для чтения, SQLite открывает с `mode=ro` и `query_only` и публикует FastCGI только на `127.0.0.1:9005`. В HTTPS server включить `deploy/attachments-nginx.conf`. У download-процесса только три переменные, без токенов бота, Gmail и MySQL. Для другого имени SQLite согласованно изменить путь в сервисах. Каталог SQLite допускает создание WAL/SHM; том `attachment-keys` веб-процессу не монтируется. Проверить чтение файлов от UID 1000.
6. Установить `ATTACHMENTS_PATH=/attachments`, `ATTACHMENTS_LINK_KEY_FILE=/private-links/signing.key`, `ATTACHMENTS_PUBLIC_BASE_URL=https://service.imenka.world/download`, `MAIL_MAX_MESSAGE_BYTES=25000000` и доступы каталога у приложения. Проверить извне GET/HEAD тестовой ссылки, точные байты и 404 неизвестного токена. Выключить запись токенов в access/error logs всех прокси. Хранилище не публиковать через `root`/`alias`.
7. Запустить процессы и проверить состояние очереди на разрешённых тестовых контактах. Только после этого включать рабочую аудиторию. Реальные клиентские отправки не относятся к локальному smoke-тесту.

Если требуется откат, остановить все процессы и восстановить согласованную версию SQLite, MySQL и файлов. Отдельный откат SQLite может повторить уже принятые доставки или рассогласовать ревизии каталога. Перед возобновлением сверить `bc_directory_operations`, снимки и статусы принятых/неопределённых частей; не переводить их массово в `pending`.
