# Локальное приложение WhatsApp

Реализация находится только в ветке `broadcast-whatsapp`. Основная логика PHP/SQLite
общая с Telegram: регистрация, согласование, переводы, очередь и отчёты. WhatsApp —
дополнительный пользовательский канал; сотрудники работают через Telegram.
Развёртывание на рабочем сервере в этот этап не входит.

## Запуск подготовленного стенда Windows

Нужны PHP 8.4+ с зависимостями Composer, Node.js для проверок и запущенный Docker Desktop.
Проверьте свободное место на системном диске Windows: Docker может хранить образы на C:,
даже когда проект расположен на D:. Данные приложения и временные файлы проверок остаются в `var` проекта.
Команды выполняются из корня проекта в PowerShell. Уже подключённая тестовая сессия
сохраняется в приватном каталоге транспорта, повторный QR при обычном перезапуске не нужен.

```powershell
.\tools\whatsapp-spike\local.ps1 start
.\tools\whatsapp\local.ps1 prepare
.\tools\whatsapp\local.ps1 status
.\tools\whatsapp\local.ps1 listen
```

`prepare` создаёт изолированную базу, применяет миграции с предварительной резервной копией
и ограничивает Windows ACL. При первом запуске необходим разрешённый тестовый номер:
`prepare -Recipient '+КОДСТРАНЫНОМЕР'`. Уже подготовленный список сохраняется; повторно
указывать номер не нужно. Отправка и входящая регистрация ограничены этим списком.
Старые события подключённой сессии до создания стенда не превращаются в новые заявки.

В окне с `listen` работает приём WhatsApp и обработка очереди. Отправьте `/start`
с разрешённого второго аккаунта на номер подключённой сессии, выберите язык и следуйте
номерным пунктам. Подтверждённый WhatsApp-номер подставляется в анкету автоматически.
Остановка приложения: `Ctrl+C`; очередь и курсор сохраняются.

Telegram, почта и переводчик в этом стенде локальные. Они не используют `.env` рабочего
бота и не обращаются к внешним API. Переводы явно помечены `[ЯЗЫК TEST]`:
это проверка маршрутизации, а не качества перевода. Настоящий переводчик в `bin/console`
остаётся DeepL. Не передавайте реальные ключи для локальной демонстрации.

Во втором окне:

```powershell
.\tools\whatsapp\local.ps1 inbox
.\tools\whatsapp\local.ps1 staff -Text '/links'
```

`inbox` выводит путь к приватному `var/whatsapp-app/live/inbox.html`; откройте файл в
браузере и обновляйте страницу. Здесь видны анкеты, письма, отчёты и подписи кнопок.
Под каждой inline-кнопкой напечатана готовая команда `callback -Text '...'`.
Выполните актуальную команду одобрения заявки. Затем `staff -Text 'Текст объявления'`,
`staff -Text 'Тема'` и команду подтверждения из нового предпросмотра. Локальный сотрудник
имеет роль суперадминистратора (ID 99), поэтому собственное объявление отправляется
после его подтверждения. Сценарий отдельного автора и согласующего проверяется в `demo`.

```powershell
.\tools\whatsapp\local.ps1 demo
```

Эта команда без сети создаёт отдельный каталог `var/whatsapp-app/demos/...` и проходит
WhatsApp-регистрацию → рассмотрение → одобрение → черновик администратора → согласование
суперадминистратором → перевод → WhatsApp/email → отчёт → привязку Telegram с подтверждением
в WhatsApp → догоняющую доставку только в новый канал. В выводе все проверки должны быть
`true`, `email_count=1`. HTML показывает весь сценарий с тестовыми анкетами.

## Привязка и идентичность

`users.id` теперь внутренний ID человека. Telegram ID и WhatsApp PN/LID находятся в
`channel_identities`; существующие Telegram ID при миграции сохраняются. Числовое
совпадение между каналами не объединяет людей. LID — непрозрачный идентификатор, его
нельзя принимать за номер телефона. Только доказанное транспортом соответствие PN/LID
создаёт alias; конфликт существующих анкет требует ручного решения.

При совпадении подтверждённого телефона `/link` отправляет запрос в первоначальный
мессенджер. В Telegram это inline-кнопка, в WhatsApp — уникальная команда `/confirm КОД`.
Она привязана к конкретной заявке и исходному аккаунту, действует 15 минут и используется
один раз. Ответ цифрой не подтверждает привязку. Не больше трёх запросов в час от одного
источника. Совпадение email, неподтверждённый LID или недоступность исходного аккаунта
ведут через `/linkhelp` к сотруднику, без раскрытия чужой анкеты.

Суперадминистратор использует `/links` и `/linkresolve ID approve|reject ПРИЧИНА`.
Решение, сотрудник и время сохраняются. Привязка сама не одобряет заявку. При одобренном
профиле подключённый канал получает последнее готовое объявление; существующие каналы
и email не получают его повторно. Следующая рассылка использует общий язык профиля.
`/unsubscribe ID` сотрудника или явная команда `/stop` пользователя прекращает все каналы.

Миграция 005 резервирует phone/email по отдельности в `contact_reservations`.
Владелец исторического контакта определяется через одобренные привязки; циклы и
неоднозначность блокируются. Это позволяет повторную подачу после ручного объединения,
сохраняя прежние `contacts` и аудит источника. Новые проверки уникальности используют
резервы, а не историческую строку `contacts`. Экспорт разделяет внутренний ID и реальные
адреса каналов; правила офлайн-восстановления приведены в [инструкции импорта](../IMPORT-USERS.md).

## Очередь, сбои и отчёты

- Аудитория, языки и адреса каналов фиксируются при одобрении. Email — один на человека.
- Каждая доставка независима. Простой WhatsApp сохраняет исходящую очередь в SQLite,
  не расходует попытки получателя и не останавливает Telegram/email. Проверка связи —
  отдельный тик, повтор не чаще чем через 60 секунд. Уведомления сотруднику — при смене состояния.
- Перед отправкой записывается намерение, после ответа — message ID и прогресс частей.
  После сбоя между ними результат `unknown`, сотрудник уведомляется атомарно.
  Автоматический повтор и `/retry` такой отправки запрещены: сначала нужно внешнее
  подтверждение результата. Обычные достоверно неуспешные задания имеют до пяти попыток.
- `accepted` означает принятие транспортом. `delivered`/`read` требуют квитанции с
  совпадающими message ID и подтверждённым адресом. Ранние и временно неразрешённые
  квитанции сохраняются, повторные события не повторяют бизнес-действия.
- Длинный текст делится без потери Unicode; учитываются лимиты символов и JSON.
  Успешные части сохраняются и не отправляются повторно. Ошибка перевода не заменяет
  перевод оригиналом, в том числе для комментариев сотрудника.

PHP не обещает exactly-once. Закреплённый SDK может повторно передать тот же кадр с тем
же message ID после разрыва соединения. Подробные ограничения, версия и источники:
[контракт транспорта](../../src/Infrastructure/WhatsApp/README.md).
Журнал входящих событий upstream ограничен семью днями, 100 000 событиями и 128 MiB:
исходящая очередь переживает долгий простой, но очень долгий простой приёмника может
потерять входящие события. Это неофициальный протокол; успешная локальная проверка не
гарантирует будущую совместимость или отсутствие ограничений со стороны WhatsApp.

## Штатный runtime и обслуживание

Для полноценного runtime добавлен `php bin/console whatsapp-poll [--once]` рядом с
`poll` и `worker`. При `WHATSAPP_ENABLED=false` старый режим сохраняется. Для включения
задайте `WHATSAPP_ENABLED=true`, `WHATSAPP_URL`, `WHATSAPP_SESSION`, `WHATSAPP_TOKEN_FILE` и
`WHATSAPP_ALLOWED_RECIPIENTS_FILE`. Token JSON содержит `session` и `token`; allowlist —
JSON-массив номеров без `+`. `check` читает эти файлы без сети и не выводит секретов.
HTTP разрешён только на loopback, HTTPS — с проверкой сертификата. В Docker loopback
относится к самому контейнеру: нельзя копировать Windows URL в отдельный контейнер
приложения без соответствующей организации сети и защищённого доступа к транспорту.

Все процессы используют одну базу. До обновления остановите `poll`, `worker`,
`whatsapp-poll` (на локальном стенде — `listen`), сохраните резервную копию и выполните
`migrate`. Автоматическая миграция при запуске рабочих процессов отключена. Команда
`migrate` сама создаёт снимок существующей базы и требует блокировки всех процессов.
Для локального стенда эти действия выполняет `prepare`; действующие анкеты не очищаются.

Для отката остановите все процессы, сохраните текущее состояние `backup`, восстановите
выбранный согласованный снимок командой `restore BACKUP_FILE --confirm` и используйте
версию кода, соответствующую снимку. Восстанавливается вся база; изменения после снимка
теряются. Не удаляйте SQLite/WAL-файлы вручную. JSON, SQLite, XLSX, HTML и данные сессии
содержат приватные данные: храните их с ограниченным доступом, не включайте в Git/образ.
Команды обслуживания читают `DATABASE_PATH` из окружения, а не из `.env`.

Для безопасности транспорт слушает `127.0.0.1:21465`, manager/webhooks/brokers отключены.
У контейнера `logging.driver: none`, поскольку upstream SDK способен печатать адреса.
PHP пишет только статусы/ID/классы ошибок; приватный HTML — пользовательский артефакт,
а не технический лог. Не открывайте этот HTML через публичный веб-сервер.

## Проверки и измерения

```powershell
node tools/whatsapp/verify.mjs store
node tools/whatsapp/verify.mjs flow
node tools/whatsapp/verify.mjs transport
node tools/whatsapp/verify.mjs integration
node tools/whatsapp/verify.mjs regression
.\tools\whatsapp\measure.ps1 -Phase idle -Seconds 20
```

PHPUnit не вызывает реальные API. `regression` выполняет `composer test`.
Замеры Docker сохраняются в `var/whatsapp-app/measurements`; доступны фазы `idle`,
`connect`, `exchange`, `recovery`. Пики — максимум периодических выборок, не аппаратный
мгновенный максимум; они характеризуют только этот стенд и нагрузку.
`probe.php` предназначен для явно разрешённой живой проверки: `long`/`recovery`/`exchange` ставят
однократное задание на единственный разрешённый номер; журнал предотвращает повторный
запуск того же теста. `inspect` выводит только технические состояния.

Фактические результаты, ресурсы и границы проверки записаны в [VERIFICATION.md](../../VERIFICATION.md).
