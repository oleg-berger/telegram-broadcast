---

Ты работаешь над расширением существующего Telegram-бота рассылок: нужно добавить WhatsApp с регистрацией пользователей и общей базой данных. Ниже зафиксированы согласованные требования. Не придумывай новый продукт и не меняй принятые решения без объяснения необходимости.

## 1. Цель проекта

Расширить существующий бот так, чтобы пользователь мог зарегистрироваться через Telegram или WhatsApp, пройти одобрение и получать текстовые объявления в подключённые мессенджеры и на email.

Основной принцип: **используем существующий функционал и расширяем возможности**. Не создаём независимый WhatsApp-бот с собственной базой пользователей и отдельной бизнес-логикой.

Работа выполняется поэтапно:

1. Проверить WhatsApp-транспорт локально.
2. Расширить существующее приложение.
3. Продемонстрировать команде полный сценарий.
4. Рассматривать развёртывание на сервере только после одобрения команды.

Этот документ описывает будущую работу. Сам по себе он не является разрешением на деплой или изменение рабочего окружения.

## 2. Существующий проект

Исходники PHP-бота находятся по адресу:

`D:\telegram-bot-source\telegram-bot`

Приложение использует PHP и SQLite, без фреймворка. Основные процессы:

- `poll` — принимает Telegram updates.
- `worker` — обрабатывает задания из SQLite.

Основные компоненты:

- `Kernel` — обработка и маршрутизация updates.
- `Registration` — регистрация пользователей.
- `Staff` — действия администраторов и суперадминистраторов.
- `Worker` — переводы, сообщения, доставки и вспомогательные задания.
- `Store` / `SqliteStore` — хранение данных и очередь.
- `Messages` и `ui.json` — готовые тексты интерфейса.
- Интерфейсы внешних сервисов: Telegram, переводчик, почта, экспорт.

Поддерживаются RU, EN-GB, ES и FR.

Есть регистрация с одобрением, возврат анкет на исправление, согласование объявлений, перевод, независимая доставка в Telegram и email, отчёты, повторы, экспорт пользователей и публикация русской копии объявления в командный Telegram-канал.

Перед проектированием повторно изучи актуальный код, README, миграции и тесты. Эти сведения описывают ранее изученную версию и не заменяют проверку текущего состояния.

**Ранее переданные в чате инструкции AGENTS.md пользователь отменил. Не восстанавливай их автоматически как действующие требования.** При начале работы проверь актуальные инструкции среды.

## 3. Среда разработки и ограничения

Разработка и реальные тесты проводятся **локально на ПК пользователя**.

Используются:

- отдельный тестовый Telegram-бот;
- отдельные настройки и токены;
- отдельная тестовая SQLite;
- отдельный WhatsApp-номер для эксперимента;
- только явно разрешённые тестовые получатели;
- только тестовые адреса email.

Не заменять рабочий Telegram-токен в производственном окружении. Создать отдельную конфигурацию тестового запуска.

Не использовать рабочую базу пользователей для отправок и не обращаться к серверу без отдельного поручения.

Будущий сервер имеет:

- 1 доступное процессорное ядро;
- около 1,9 ГиБ RAM;
- на момент проверки около 1,3 ГиБ доступной памяти;
- 2 ГиБ swap;
- диск около 20 ГБ;
- уже работающие MySQL, PHP и nginx.

Сейчас PHP-бот развёрнут без Docker. Требуется экономное использование ресурсов и минимум дополнительных сервисов.

Эти показатели — снимок состояния, а не гарантия доступных ресурсов при будущем деплое.

## 4. Выбранный WhatsApp-транспорт

**Первый кандидат для локальной проверки — WPPConnect Server Go:**

https://github.com/wppconnect-team/wppconnect-server-go

Причины выбора:

- Go;
- использование whatsmeow;
- отсутствие необходимости в Chromium/Puppeteer;
- встроенная SQLite;
- отсутствие обязательной внешней серверной СУБД;
- заявленные HTTP API, webhooks и восстановление сессий.

Это предварительный выбор, который нужно подтвердить проверкой конкретного релиза.

Evolution API рассматривался, но штатно требует PostgreSQL либо MySQL. SQLite в проверенной актуальной конфигурации не поддерживалась. Redis необязателен. Пользователь не хочет добавлять тяжёлую инфраструктуру ради одного WhatsApp-канала.

Не следует:

- начинать с Evolution API без пересмотра решения;
- писать собственный мост на Baileys — пользователь предпочёл готовый транспорт;
- обещать конкретный расход памяти без замеров;
- считать язык Go доказательством достаточной надёжности;
- переносить базу PHP-бота в MySQL/PostgreSQL.

WPPConnect обслуживает WhatsApp как транспорт. Его техническая SQLite отделена от основной SQLite приложения.

Используемое подключение является неофициальным. Оно не требует токена Meta Cloud API и официального Coexistence, но зависит от протокола WhatsApp и несёт риск отключений и блокировки номера. Это уже обсуждалось. Рабочую пригодность для рассылок нельзя считать доказанной успешным локальным тестом.

## 5. Общая архитектура

Сохранить PHP-приложение центром системы:

- пользователи и анкеты;
- одобрения;
- привязки мессенджеров;
- языки;
- объявления и переводы;
- очередь;
- отчёты;
- повторные попытки.

WPPConnect отвечает за соединение с WhatsApp, приём и отправку сообщений и доступные статусы.

Входящие WhatsApp-события должны попадать в приложение через адаптер. Исходящие сообщения выполняются через очередь приложения.

Нужно сохранить разделение транспорта и бизнес-логики. Не копировать `Registration` целиком в отдельную реализацию WhatsApp, которая со временем начнёт отличаться.

Точный способ приёма webhooks, авторизации локального взаимодействия и запуска PHP-приёмника определить после проверки возможностей транспорта. Не добавлять тяжёлый фреймворк без необходимости.

## 6. База пользователей

**Одна общая база пользователей в SQLite.**

Один человек может иметь:

- Telegram;
- WhatsApp;
- email.

Нужно отделить внутреннюю личность пользователя от идентификаторов мессенджеров. В изученной версии `users.id` фактически являлся Telegram ID — нельзя использовать WhatsApp-номер как взаимозаменяемое значение этого поля.

Перед изменениями составить схему совместимой миграции:

- внутренний пользователь;
- привязки каналов;
- идентификаторы Telegram и WhatsApp;
- подтверждение привязки;
- состояние доступности каналов;
- временные запросы подключения;
- необходимые изменения заданий доставки.

Существующие пользователи, заявки, контакты, объявления, задания и история не должны теряться.

Новые миграции добавлять отдельно, не переписывая уже применённые.

## 7. Регистрация

### Главное требование

**Тексты регистрации должны быть точно такими же, как в существующем Telegram-боте.**

Использовать имеющиеся `Messages/ui.json` на четырёх языках. Не писать новые приветствия, вопросы, объяснения и меню вместо существующих.

Сохранить:

- порядок шагов;
- поля анкеты;
- проверки;
- навигацию назад;
- исправление полей;
- предварительный просмотр анкеты;
- отправку заявки;
- одобрение, отклонение и возврат на исправление.

Адаптировать только способ взаимодействия с транспортом:

- по возможности использовать подходящие элементы WhatsApp;
- если Telegram-кнопки нельзя воспроизвести, сохранить их подписи и смысл;
- допустимы пронумерованные варианты и ответы цифрами;
- не менять содержание самого текста регистрации ради адаптации.

Новые тексты допустимы для действительно новых функций: привязки второго мессенджера, её подтверждения и связанных результатов.

### Телефон в WhatsApp

Если транспорт достоверно предоставляет номер собеседника, использовать его как телефон анкеты без повторного ручного ввода.

Не предполагать, что любой WhatsApp ID является номером телефона. Проверить работу с JID/LID и доступными сопоставлениями.

Если номер нельзя достоверно определить, предусмотреть получение и подтверждение номера отдельно. Конкретный способ требует технического исследования и не должен быть выдуман как уже согласованный.

### Язык

Язык един для пользователя и всех каналов.

Изменение через любой привязанный мессенджер действует на будущие рассылки в Telegram, WhatsApp и email. Не менять задним числом снимки уже созданных рассылок без отдельного решения.

## 8. Правила доставки

По умолчанию:

| Где зарегистрировался человек | Куда получает объявления |
|---|---|
| Telegram | Telegram + email |
| WhatsApp | WhatsApp + email |

Не добавлять в регистрацию свободный выбор каналов.

Если человек явно подключил второй мессенджер, получает:

**Telegram + WhatsApp + email.**

При этом email отправляется один раз на пользователя для конкретного объявления, а не по разу на каждую привязку.

Объявления содержат только текст. Рассылка фотографий, видео, документов и голосовых не входит в задачу.

Существующий порядок создания, согласования и перевода объявлений сохраняется.

## 9. Подключение второго мессенджера

Пример: человек уже зарегистрирован в Telegram и приходит в WhatsApp.

1. Находим возможное совпадение с существующей анкетой.
2. Не раскрываем анкету и не объединяем пользователей автоматически.
3. Предлагаем подключить второй мессенджер.
4. Запрашиваем подтверждение через уже привязанный мессенджер.
5. После подтверждения добавляем новый канал.
6. Старый канал остаётся подключённым.

Аналогичный сценарий нужен в обратном направлении: WhatsApp → Telegram.

Запрос подтверждения должен быть одноразовым, ограниченным по времени и привязанным к конкретным пользователю и новому аккаунту. Просроченные, повторные и чужие подтверждения безопасно отклоняются.

Точное время действия и ограничения частоты — технические параметры, которые нужно обосновать в проекте.

**Повторное одобрение анкеты суперадминистратором не требуется**, если пользователь уже одобрен и связь аккаунтов подтверждена.

Если заявка ещё ожидает одобрения, второй канал можно подтвердить, но доставка объявлений начинается только после общего одобрения.

### Неоднозначные случаи

- Совпадает только email, телефон отличается → передать сотруднику.
- Нет доступа к первому мессенджеру → передать сотруднику.
- Нельзя достоверно установить связь → не объединять автоматически.

Сотруднику нужен явный, проверяемый способ разрешить ситуацию. Не раскрывать персональные данные неподтверждённому собеседнику.

## 10. Управление сотрудниками

Все действия сотрудников остаются в Telegram:

- просмотр заявок;
- одобрение;
- возврат на исправление;
- отклонение;
- комментарии;
- подготовка объявления;
- согласование;
- запуск;
- просмотр результатов и повтор ошибок.

В карточке заявки и отчётах должно быть достаточно информации о доступных каналах, чтобы сотрудник понимал состояние пользователя.

WhatsApp-интерфейс администратора не нужен.

Существующие роли и ограничения доступа сохраняются.

## 11. Последнее готовое объявление

Сохранить догоняющую доставку:

- При первом одобрении пользователь получает последнее готовое объявление в зарегистрированный мессенджер и на email.
- При подключении второго мессенджера последнее готовое объявление отправляется **только в новый канал**.
- Ранее успешные Telegram/email/WhatsApp-доставки не повторяются.
- Если нового задания фактически не появилось, не создавать повторные отчёты без причины.

## 12. Отписка

Пользователь отказался от добавления отдельной кнопки отключения рассылки в текущем мессенджере, чтобы не загромождать интерфейс.

Сохранить полную отписку сотрудником, которая прекращает доставку во всех каналах.

Отсутствие кнопки не трактовать как требование игнорировать явные просьбы прекратить сообщения. Не расширять интерфейс без обсуждения.

## 13. Очередь, ошибки и восстановление

Доставки в Telegram, WhatsApp и email независимы.

Если WhatsApp отключился:

- email и Telegram продолжают работать;
- WhatsApp-задания сохраняются;
- сотрудник получает уведомление;
- после восстановления отправляются все пропущенные объявления в порядке очереди, даже после нескольких дней;
- ожидающие доставки не считаются успешными.

Различать:

- недоступность общей WhatsApp-сессии;
- временную ошибку конкретной отправки;
- постоянную ошибку получателя;
- принятие сообщения транспортом;
- доставку;
- неопределённый результат.

Не расходовать бесконечно попытки каждого получателя при общем отключении транспорта. Не блокировать остальные виды заданий ожиданием WhatsApp.

Не создавать уведомление сотруднику на каждом тике: состояние отключения и восстановления должно обрабатываться без спама.

### Неопределённая отправка

Если соединение оборвалось после отправки запроса и неизвестно, было ли сообщение принято:

1. Попытаться сверить результат по доступным идентификаторам и событиям.
2. Если результат установить нельзя, отметить его как неопределённый.
3. Сообщить сотруднику.
4. Не повторять слепо.

Не обещать абсолютную доставку «ровно один раз», если транспорт не даёт соответствующих гарантий.

Проверить, есть ли в выбранном релизе транспортная очередь и автоматические повторы. Не допускать, чтобы PHP и WPPConnect независимо повторяли одну отправку и создавали дубли.

Длинные сообщения должны делиться с сохранением прогресса. Проверить реальные ограничения WhatsApp-транспорта, не переносить лимиты Telegram механически.

## 14. Сохранение существующих гарантий

Не ослаблять текущую защиту приложения:

- рассылка начинается только после одобрения;
- повтор входящего события не повторяет бизнес-действие;
- старые кнопки и подтверждения безопасны;
- аудитория и необходимые параметры доставки фиксируются при одобрении;
- исходный текст не заменяет отсутствующий перевод;
- успешные доставки и части не отправляются заново при обычном повторе;
- ошибки одного канала не отключают другие;
- анкеты, тексты, телефоны, email, токены и сессии не попадают в логи;
- статусы отражают фактически известный результат.

Telegram updates и WhatsApp-события должны иметь отдельные пространства идентификаторов для дедупликации.

Технические данные WPPConnect и резервные копии сессий считать секретными. Его настройки логирования проверить отдельно: безопасность PHP-логов не защищает от утечки через транспорт.

## 15. Этап 1 — исследование и локальная проверка транспорта

До большой доработки приложения:

1. Проверить актуальный репозиторий WPPConnect Server Go.
2. Выбрать и закрепить конкретный релиз или commit.
3. Проверить лицензию, зависимости, поддерживаемый запуск на Windows и Linux.
4. Изучить авторизацию API, SQLite, хранение сессии, webhooks, повторы и статусы.
5. Запустить локально с отдельной конфигурацией.
6. Подключить тестовый WhatsApp через предусмотренную процедуру.
7. Проверить приём и отправку текста только разрешённым участникам.
8. Проверить кириллицу, акценты, эмодзи, переносы и длинные тексты.
9. Проверить восстановление после перезапуска процесса и отключения сети.
10. Проверить повторы webhooks и доступные способы сверки неопределённой отправки.
11. Измерить RAM и CPU в простое, при подключении, обмене сообщениями и восстановлении.

Не публиковать API в интернет без необходимости. Для локального взаимодействия предпочесть loopback и авторизацию.

### Результат этапа

Краткий отчёт:

- что работает;
- какие возможности реально подтверждены;
- что не поддерживается;
- замеры ресурсов;
- оставшиеся риски;
- рекомендация продолжать либо пересмотреть транспорт.

Если транспорт не подходит, не подменять его молча. Объяснить конкретную причину и согласовать альтернативу.

- общую модель пользователя и привязок;
- адаптер входящих WhatsApp-событий;
- интерфейс отправки;
- переиспользование регистрации;
- адаптацию существующих сообщений и элементов управления;

- изменения очереди и отчётов;
- поведение при сбоях и неопределённых отправках;
- изолированную локальную конфигурацию;

Отдельно отметить решения, которые являются предложением разработчика, а не утверждённым требованием пользователя.

## 17. Этап 3 — реализация и автоматические проверки

Реализовывать небольшими проверяемыми частями:

1. Модель пользователя и каналов, миграция.
2. Приём и дедупликация WhatsApp-событий.
3. Общий сценарий регистрации.
4. Адаптация существующих UI-текстов.
5. Одобрение WhatsApp-заявок в Telegram.
6. Привязка второго мессенджера.
7. WhatsApp-доставка через очередь.
8. Догоняющая доставка.
9. Статусы, отчёты, повторы и отключения.
10. Локальные инструкции запуска и измерений.

В автоматических тестах использовать фейки транспорта, переводчика и почты. Реальные аккаунты не должны требоваться для запуска тестового набора.

Проверять существующие сценарии Telegram/email на регрессии.

## 18. Приёмочные сценарии

Обязательные проверки:

1. Новый пользователь регистрируется только через WhatsApp.
2. Используются существующие тексты регистрации на всех четырёх языках.
3. Исправление анкеты и навигация работают.
4. Заявка приходит сотруднику в Telegram.
5. Одобрение, возврат и отклонение работают.
6. Комментарий сотрудника переводится и доставляется.
7. До одобрения объявления не отправляются.
8. После одобрения пользователь получает WhatsApp + email.
9. Telegram-пользователь продолжает получать Telegram + email.
10. Подключение второго мессенджера подтверждается через первый.
11. После подключения работают три канала, email не дублируется.
12. Обратная привязка WhatsApp → Telegram работает.
13. Старые и повторные подтверждения не создают привязки.
14. Совпадение только email не приводит к автоматическому объединению.
15. Последнее объявление доставляется по согласованным правилам.
16. Смена языка применяется к будущим рассылкам во всех каналах.
17. Сбой WhatsApp не мешает Telegram/email.
18. После восстановления продолжается накопленная очередь.
19. Неопределённый результат не вызывает слепой повтор.
20. Повторные события не повторяют регистрацию, одобрение и отправки.
21. Полная отписка сотрудником прекращает все каналы.
22. Логи не содержат персональные данные и секреты.
23. Неавторизованные тестовые получатели не получают сообщений.
24. Перезапуск сохраняет прогресс и сессию.
25. Замерены ресурсы, включая пики.

## 19. Что не входит в задачу

- Развёртывание на рабочем сервере до одобрения команды.
- Перенос основной базы с SQLite.
- Создание собственной CRM.
- Интеграция с МойСклад.
- Переписывание текстов регистрации.
- Новый интерфейс управления в WhatsApp.
- Рассылка вложений.
- Свободный выбор каналов при регистрации.
- Отдельная кнопка отключения одного канала.
- Подключение рабочего номера компании для первого эксперимента.
- Обход ограничения Meta путём создания новых официальных аккаунтов.

## 20. Критерий завершения локального этапа

Команда должна увидеть полный работающий сценарий:

**Регистрация в WhatsApp → рассмотрение в Telegram → одобрение → создание и согласование объявления → перевод → независимые доставки → отчёт.**

Дополнительно должны быть продемонстрированы:

- подключение второго мессенджера;
- отсутствие повторной регистрации одного человека;
- восстановление после отключения;
- обработка неопределённой отправки;
- измеренное потребление ресурсов.

Успешный локальный тест не равен разрешению на деплой. Развёртывание на сервере — отдельный следующий этап после одобрения команды.
